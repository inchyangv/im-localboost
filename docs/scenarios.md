# 동작 시나리오

사용자가 실제로 겪을 수 있는 상황을 화면별로 정리한 문서입니다. 각 항목은 "어떤 상황에서 무엇이 보이는가"를 적고 그렇게 동작하는 근거를 함께 표시합니다. 발표용 진행 순서는 [demo.md](demo.md)에, 설계 요약은 [README](../README.md#동작-방식)에 있습니다.

근거 표기: **C**는 컨트랙트 `DalgubeolPay`, **E**는 엔진, **W**는 웹의 규칙입니다.

수치는 데모 시드 값을 전제합니다.

| 상한 | 값 |
| --- | --- |
| 최대 보너스율 | 15% (`maxRateBps` 1500) |
| 건당 보너스 상한 | 3,000원 |
| 1인 일일 보너스 상한 | 5,000원 |
| 상권 시간당 집행 상한 | 300,000원 |
| 가맹점 슬롯 상한 | 기준 매출 100,000원/시간의 150% = 150,000원 |
| 보류 지연, 상한 변경 지연 | 각 60초 |
| 서명 유효 시간 | 120초 |

## 1. 진입

화면은 두 영역으로 나뉩니다. 소비자 앱(`/`, `/pay`, `/map`, `/history`)은 연결한 지갑으로만 동작하고 관리자 도구(`/admin` 아래)는 상단에서 데모 계정을 고릅니다. 옛 주소 `/merchant`와 `/city`는 `/admin/merchant`와 `/admin/city`로 리다이렉트됩니다.

| # | 상황 | 보이는 것 | 근거 |
| --- | --- | --- | --- |
| 1-1 | 지갑을 연결하지 않고 `/`를 열기 | 랜딩 화면: 지금 상권별 보너스율, "지갑 연결", "가맹점 지도 보기" | W |
| 1-2 | "지갑 연결" | EIP-6963으로 감지된 지갑(Kaia Wallet, MetaMask 등) 목록에서 고릅니다. 연결되면 상단에 체인 표시와 주소가 나옵니다. 주소 메뉴에서 가스 잔액 확인, 주소 복사, 탐색기, faucet, 연결 해제를 할 수 있습니다. | W |
| 1-3 | 지갑의 네트워크가 앱과 다름 | 빨간 "잘못된 네트워크" 표시와 "네트워크 전환" 배너가 나옵니다. 결제 버튼을 누르면 전환을 먼저 시도합니다. | W `wallet_switchEthereumChain` |
| 1-4 | 처음 연결한 지갑(`personId` 없음) | 지갑 카드에 "은행 미등록"이 표시되고 결제 버튼이 비활성입니다. "은행 등록하고 시작 자금 받기"를 누르면 은행이 `personId` 연결, iMKRW 100,000원 발행, 0.2 KAIA 전송을 트랜잭션 최대 3건으로 처리합니다. | E `POST /onboard`, C `UnregisteredPayer` |
| 1-5 | 같은 KST 날에 시작 자금을 다시 요청 | "오늘은 이미 받았어요". 다음 날 다시 받을 수 있습니다. | E 하루 1회 |
| 1-6 | 은행 계정의 KAIA가 부족한 상태에서 온보딩 | `personId` 연결과 iMKRW 발행은 진행되고 가스 전송만 건너뜁니다. 화면이 Kaia faucet과 "내 주소 복사"를 안내합니다. | E `gasSkipped` |
| 1-7 | 지갑의 KAIA가 결제 수수료보다 적음 | "수수료용 KAIA가 부족해서 결제를 보낼 수 없어요."와 faucet 링크가 나옵니다. | W |
| 1-8 | 엔진이 꺼져 있음 | 상단의 엔진 상태 표시가 빨강이 됩니다. 결제 내역, 위험 로그, 율 표가 마지막 값에서 멈춥니다. 결제는 `/attest`가 먼저 실패하므로 트랜잭션을 보내지 않습니다. | W 엔진 우선 호출 |
| 1-9 | RPC가 느리거나 끊김 | 잔액과 크레딧이 늦게 표시되고 트랜잭션 확인 대기가 길어집니다. Kairos 공개 RPC에서는 수 초가 보통입니다. | - |
| 1-10 | 관리자 도구를 권한이 맞지 않는 데모 계정으로 열기 | 화면마다 필요한 계정을 안내하는 게이트가 나옵니다(예: `/admin/bank`는 "은행 데모 계정을 고르면…"). | W `PersonaGate` |

### 2.2 정상 결제

결제는 "엔진 위험 판정 → 지갑 서명 → 온체인 결제" 순으로 진행됩니다. allowance가 부족한 지갑은 approve 트랜잭션을 먼저 승인합니다.

| # | 상황 | 결과 | 근거 |
| --- | --- | --- | --- |
| 2-7 | 율이 게시된 상권의 가게에 오늘 처음 결제 (예: 북성로 10%, 10,000원) | 보너스 1,000원이 적립됩니다. 잔액 −10,000, 크레딧 +1,000, 가맹점 +10,000. 결과 카드에 tier, 점수, 트랜잭션 링크가 나옵니다. | C `boost = base × rate / 10000` |
| 2-8 | 크레딧을 일부 사용 (예: 10,000원 중 크레딧 1,000원) | 보너스는 현금분 9,000원 기준인 900원입니다. 크레딧 −1,000, 잔액 −9,000 | 불변식 4, C `base = amount − useCredit` |
| 2-9 | 보너스가 건당 상한을 넘는 금액 (예: 15% 상권에 30,000원 → 4,500원) | 보너스가 3,000원으로 잘립니다. | C `min(boost, perTxBoost)` |
| 2-10 | 오늘 누적 보너스가 5,000원에 근접 (예: 잔여 500원) | 보너스가 500원으로 잘립니다. | C `personDailyBoost − personDay` |
| 2-11 | 가맹점의 이번 시간 매출이 슬롯 상한에 근접 | 상한까지 남은 금액만 보너스 대상이 됩니다(남은 금액이 5,000원이면 10,000원을 결제해도 5,000원분만 계산). | C 슬롯 상한 |
| 2-12 | 상권의 시간당 집행 또는 예산이 부족 | 남은 만큼만 지급합니다. | C `zoneHourlyCap`, `zoneBudget` |
| 2-13 | 매시 정각부터 45초 사이에 결제 | 버튼이 카운트다운을 보여 준 뒤에 `/attest`를 호출합니다. 위험 모델이 율 변경 직후의 결제에 민감하기 때문입니다. | W, E `secs_since_rate_change` |

### 2.3 결제는 성공하고 보너스만 0원

결제 자체는 막히지 않습니다(불변식 1). 결과 카드에 "보너스 없이 결제됐어요"와 사유 한 줄이 나오며 같은 사유가 미리보기 단계에서도 먼저 보입니다. 여러 사유가 동시에 해당하면 아래 표의 순서에서 첫 번째만 표시합니다(`web/src/lib/reasons.ts`).

| 순서 | 상황 | 사유 문구 | 근거 |
| --- | --- | --- | --- |
| 1 | 엔진이 tier 2로 판정 | "위험 등급 2: 보너스 미지급 (환류, 모델 점수)"처럼 사유 코드가 함께 표시됩니다. | E, C |
| 2 | 결제 금액 전액을 크레딧으로 냄 | "크레딧 결제분에는 보너스가 없음" | 불변식 4 |
| 3 | 같은 가게에서 오늘 이미 보너스를 받음 | "오늘 이미 보너스를 받은 가게" | C `pairDay` |
| 4 | 이 시간에 그 상권의 율이 게시되지 않았거나 0% | "현재 시간 보너스율 0%" | C `rates[zone][hour]` |
| 5 | 가맹점이 이번 시간 슬롯 상한을 다 씀 | "가맹점 슬롯 상한 도달" | C |
| 6 | 오늘 개인 보너스 5,000원을 다 받음 | "오늘 개인 보너스 한도 소진" | C |
| 7 | 상권이 시간당 300,000원을 다 집행함 | "상권 시간당 한도 소진" | C |
| 8 | 상권 예산이 0원 (예: 시드 직후의 북성로) | "상권 예산 소진" | C |

`pairDay`는 보너스가 0보다 크게 확정된 결제에서만 기록됩니다. 그래서 tier 2로 차단된 결제 뒤에 같은 가게에 다시 결제해도 3번 사유가 나오지 않고 위험 판정을 다시 받습니다.

### 2.4 보류 (tier 1)

| # | 상황 | 보이는 것 | 근거 |
| --- | --- | --- | --- |
| 2-14 | 엔진이 tier 1로 판정 (환류·쌍 반복·매출 이탈 규칙, 또는 모델 점수 0.5 이상 0.8 미만) | 결과 카드에 보류된 보너스 금액, 보류 번호, "보류: N초 뒤 지급 가능 (환류)"가 나옵니다. 크레딧은 아직 늘지 않고 상권 예산은 이미 차감됩니다. | C Pending 생성 |
| 2-15 | 60초 뒤에 누군가 `/admin/bank`에서 "지급 가능"을 실행 | 크레딧에 반영됩니다. | C `release()`는 누구나 호출 |
| 2-16 | 은행이 지급 전에 "예산으로 환수" | 크레딧에 반영되지 않고 상권 예산으로 돌아갑니다. 시민에게 별도 알림은 없습니다. | C `clawback()` BANK_ROLE |
| 2-17 | 시드 직후의 신규 지갑으로 담합 패턴 결제 | 규칙은 tier 1이어도 모델이 0.8 이상을 주면 tier 2로 올라가 2.3절 1번이 됩니다. | E `max(규칙, 모델)` |

### 2.5 결제 실패 (revert)

"결제에 실패했어요" 아래에 한국어 메시지와 에러 이름이 표시되고 결과 카드는 뜨지 않습니다. 메시지는 `web/src/lib/errors.ts`에 있습니다.

| 상황 | 메시지 (에러 이름) |
| --- | --- |
| 서명 발급 후 120초가 지나서 전송됨 (지갑 승인 지연, RPC 지연) | 서명이 만료되었습니다 (`AttestationExpired`) |
| 같은 서명을 다시 제출 | 이미 사용된 서명입니다 (재사용 차단) (`NonceUsed`) |
| 서명 내용과 결제 인자가 다름 | 서명 내용이 결제 내용과 일치하지 않습니다 (`AttestationMismatch`) |
| 엔진의 attester 키가 컨트랙트에 등록된 것과 다름 (배포와 엔진의 불일치) | 서명자가 등록된 attester가 아닙니다 (`BadSigner`) |
| `personId`가 연결되지 않은 지갑 | 등록되지 않은 결제자입니다 (`UnregisteredPayer`) |
| 비활성 가맹점 | 비활성 가맹점입니다 (`MerchantInactive`) |
| iMKRW 잔액 부족 | iMKRW 잔액이 부족합니다 (`ERC20InsufficientBalance`) |
| approve가 실패했거나 거절됨 | iMKRW 사용 승인(allowance)이 부족합니다 (`ERC20InsufficientAllowance`) |
| 크레딧 초과 사용이 폼 검증을 우회함 | 크레딧 잔액이 부족합니다 (`InsufficientCredit`), 크레딧 사용액이 결제 금액을 초과합니다 (`CreditExceedsAmount`) |
| 트랜잭션은 성공했지만 `Paid` 이벤트를 찾지 못함 | 실패가 아니라 경고 카드 "결제는 성공했지만 Paid 이벤트를 찾지 못했어요"와 트랜잭션 링크 |

## 3. QR 결제 (가맹점 제시형)

| # | 상황 | 보이는 것 | 근거 |
| --- | --- | --- | --- |
| 3-1 | 가맹점이 `/admin/merchant`의 "결제 QR"에 금액 입력 → "QR 만들기" | QR 이미지(내용은 `<사이트>/pay?m=<가맹점>&a=<금액>&r=<참조 8자>`), 금액, 참조, "링크 복사", "결제 대기 중" 배지. 금액 입력은 잠깁니다. 1,000원 미만은 만들 수 없습니다. | W `QrPanel` |
| 3-2 | 손님이 폰의 기본 카메라로 QR을 찍음 | 같은 사이트의 `/pay` 링크가 열립니다. | QR 내용이 URL |
| 3-3 | 손님이 `/`의 "QR 스캔" 사용 | 카메라 모달이 열립니다. 기기 내장 인식(`BarcodeDetector`)이 있으면 그것을 쓰고 없으면 jsQR로 해석합니다. 인식하면 `/pay`로 이동합니다. | W `QrScanner` |
| 3-4 | 카메라 권한 거부, HTTP 접속, 미지원 브라우저 | 안내 문구와 "결제 링크 붙여넣기" 입력으로 대체합니다. | W |
| 3-5 | 다른 사이트의 QR 또는 임의의 문자열 | "달구벌페이 결제 QR이 아니에요." | W `parsePayInput` |
| 3-6 | `/pay`가 열림 | 가맹점 이름·상권·업종, 고정된 금액, 크레딧 사용 입력, 예상 보너스와 사유, 결제 버튼. 결제 흐름과 0원 사유는 `/`와 같습니다. 지갑 미연결·미등록·네트워크 불일치도 1절과 같이 처리합니다. | 불변식 유지 |
| 3-7 | 링크의 가맹점이 미등록이거나 금액 형식이 잘못됨 | "이 결제 링크는 열 수 없어요"와 소비자 화면 링크 | W `parsePayParams` |
| 3-8 | 결제 완료 | `/pay`에 결과 카드가 나오고 가맹점 화면은 5초 안에 "결제 완료"와 금액·보너스·tier·트랜잭션을 보여 줍니다. "새 QR 만들기"로 다음 결제를 받습니다. | E `/payments?merchant=` 폴링 |
| 3-9 | 같은 금액의 다른 결제가 먼저 들어옴 | 참조값은 온체인에 없으므로, QR을 만든 뒤에 들어온 같은 금액의 `Paid`를 완료로 봅니다. QR을 만들기 전의 결제는 제외합니다. 프로토타입의 한계입니다. | W 매칭 규칙 |

## 4. 가맹점 데스크 (`/admin/merchant`)

가맹점으로 등록된 지갑을 연결하거나 데모 계정 "가맹점 1~3"을 고르면 열립니다. 나머지 가맹점은 수취 전용 주소로 등록되어 있어서 결제는 받을 수 있지만 이 화면에 들어올 계정이 없습니다.

## 8. 시간과 상태의 경계

| 상황 | 영향 |
| --- | --- |
| KST 자정 | `pairDay`와 개인 일일 한도가 초기화되어 같은 가게에서 다시 보너스를 받을 수 있습니다. 엔진은 자정을 감지하면 `k`를 하루 한 번 보정합니다(`clamp(planned/actual, 0.5, 1.5)`, 실집행이 0이면 1.5). |
| 정시 | 슬롯 게이지와 상권 시간당 집행이 초기화됩니다. 율은 다음 시간 게시분으로 바뀌고 없으면 0%입니다. |
| 컨트랙트 재배포 | 주소와 시드가 새로 생기므로 엔진과 웹도 다시 배포해야 합니다([deploy.md](deploy.md)). 엔진 DB에 옛 기록이 남아 있으면 결제 내역과 위험 로그에 섞여 보일 수 있습니다. |
| 엔진 재시작 | 폴러가 DB의 마지막 블록부터 이어서 읽습니다. DB가 비어 있으면 `startBlock`부터 다시 읽어 결제 이력을 복구하지만 위험 판정 로그는 `/attest` 시점의 기록이어서 복구되지 않습니다. |
| 폴러가 뒤처짐 | 방금 일어난 환류 Transfer를 엔진이 아직 읽지 못해서 환류 규칙이 걸리지 않을 수 있습니다. 담합 링 데모는 3초 대기로 이를 완화합니다. |
